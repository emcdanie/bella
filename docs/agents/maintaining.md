# Maintaining BELLA — rules for agents working on the system

Rules for any AI agent reading, writing, or building BELLA itself. These are not suggestions. Follow them, or the output is wrong.

BELLA is the design system for **ctrl_alt_design** (Elleta McDaniel's design engineering practice). It powers `elleta.design`, CHIP, and everything downstream. Its job is to keep that work editorial, deliberate, and recognizably not-AI-generic.

## READ FIRST: how BELLA is built (every session, every brief pastes this block verbatim)

### Governance: who decides, and how a change moves

**Every Figma write ends with two checks, both pasted in the report:** pixel-check (figma-pixel-perfect skill) and `docs/agents/craft-check.js` (this block as code: rules 1, 7, 9, 10, 12, 13, 14, the 16px floor, line height 1.5, the two fonts, screens as template instances). Pass = 0, or each remaining line is a named exception in the part description. decided 18 Nov 2026. When she catches something craft-check missed, add a check for it the same day.

**Screen score (the 18 Nov scored audit, so re-scores compare like for like).** Each screen 0–100: pixel-perfect 20 (pixel-check: CLIPPED, SPILLS, OFF-CENTRE, OFF-SIZE, TEXT-SPILL, subpixel; content-hugging OFF-SIZE and fitting two-line TRUNCATED not counted), craft 20 (craft-check on the screen and its Content component, R13 logo lines ignored), built from the system 20 (share of visible nodes inside published BELLA instances; local CHIP parts count as loose), tokens 15 (fills, strokes, gaps, padding, radius bound), code-ready 15 (no detached instances, auto layout on every container, no fixed-height text, real content, one part per job), looks right 10 (1x screenshot judged for alignment, rhythm, cramped or empty areas). Pass = 85+ with no fail in "built from the system" or "code-ready".

**Code starts page by page** (decided 18 Nov 2026): a flow goes to code once it scores 85+ on the scored audit, passes the clean-data gate (guideline 5), its library parts are published, and she has said yes to its look by name. Plan: chip/docs/plans/code-build-2026-11.md.

**Playbooks is called "Not again"** (decided 19 Nov 2026): the page and its items say "Not again"; "Recipes" is Brad Frost's term for product compositions, so never use it here. **Playbooks ("Not again") is the first page in code** (decided 19 Nov).

**Nothing made is lost** (decided 18 Nov 2026). Before a page is rebuilt in code, every feature that exists only in code is listed with a picture; she decides for each: add to Figma, keep in code, or retire. A rebuild never overwrites a code-only feature she has not decided on.

**Publish in batches.** The library writer finishes a batch, audits it, stops writing and says "batch N ready"; she publishes once; the next batch starts only after her "done". Never write to a library while she is publishing (decided 18 Nov 2026).

**Nothing reaches her unaudited.** Before any picture or "done" goes to Elleta, the sender (session or coordinator) audits it: run craft-check and pixel-check, then the content sweep (no placeholder or repeated copy, every count says what it counts, no small Segmented control on a main page, standard tokens such as the container padding looked up rather than chosen), then a ui-polish-pass look at 1x against the rules list. ### Guidelines: how BELLA looks and is used

1. **Tokens follow Subatomic.** Tier 1 plain scale, tier 2 shared meaning, tier 3 a part's own token only when it must differ. Use the shared colours already outlined. Spacing and sizes come from the plain scale. Themes and tones change colour, font face and corners only, never sizes, spacing, edges or type. *Check: ds-token-architecture.*
2. **Parts follow Atomic.** One part per job, built from library parts. A message is a Notification, not a Card. Any mark used in two parts (a bar, an icon circle, an arc, a status mark) is its own part first, and an existing part that nearly does the job (Progress, Stat, StatusDot) is amended before anything new is drawn. Elleta, 18 Nov 2026, after the bar and icon circle were drawn separately in three new parts: "why are they not components it themselves why arent we building atomically". *Check: ds-architect; no drawn layer group appears in two parts.*
3. **Where the course is silent, do what the big libraries do** (Material 3, Carbon, Polaris, Atlassian, Primer): states, naming, sizes, disabled. Cite them. Read Brad's lesson itself, not a summary.
4. **AAA** (section below).
7. **Build parts the way code builds them.** Every part is auto layout all the way down, as flexbox would lay it out. No absolute position except overlays code also positions absolutely (focus ring, scrim, badge on an avatar), and each of those is named in the part description. A close or dismiss button sits in the flow (a row: content fills, button hugs) with the part padding around it, never pinned to a corner. Every tap target is 44. decided 18 Nov 2026. *Check: construction lint (absolute children, non-auto-layout frames, fixed-height text, targets under 44) reads 0 per part.*
9. **No one-side edges on rounded shapes.** A coloured edge on one side only (left stripe, top bar) bends along the corner and looks wrong. To mark a card, lane or panel, use a full border all the way round (2px, 3:1 against its background), or a wash. decided 18 Nov 2026. *Check: no inset or border on only one side of anything with a radius.*
10. **Spacing groups by meaning, on the 4-point scale.** Inside a group (title and subtitle, label and value) 4; between a mark and its labels (arc and Low/High, bar and caption) 8 to 12; between groups inside a card 24; between cards 24. A gap inside a group is never bigger than the gap between groups, and a drawing's own box fits its marks (no hidden padding, nothing clipped). decided 18 Nov 2026. *Check: print the gaps between a card's groups; every one is 4, 8, 12 or 24 and follows this order.*
11. **Numbers only where there is an order.** Numbered pins (01, 02...) mark a real sequence, such as the Work lanes (Needs you, Claude, Gate, Ready). Sections with no order get their icon circle instead. Elleta, 18 Nov 2026, on "01 System health": "also why is there a number here.??". *Check: every numbered marker belongs to a sequence a person moves through.*
12. **Arrows go, buttons do.** One arrow (›, Iconoir nav-arrow-right, always the Trailing part: a 24 frame that fills the row height so the glyph is centred, with a 44 Hit area; the glyph is drawn 8×16 at stroke 1.5, measured from her reference chevron (decided 18 Nov); the same part carries ↗ for links that leave and ⇅ for the switcher; decided 18 Nov; replaces 20) means "open where you see more": card headers, list rows, "See all". It sits at the row's right edge and the whole row is the target (44 tall). A button changes something (Set target, Add pairs, Send to Claude, Run the gate). Never a button that only navigates ("Show the 9"), never an arrow that does a job. A count says of what and which way ("9 of 44 fail", "251 of 264 pass"; 18 Nov: "9 or 44 pass or dont ??"). decided 18 Nov 2026. *Check: list every arrow and button on a page; each arrow navigates, each button acts.*
13. **One logo per job, and dots only mean status.** The app logo once (the rail), the client logo once (the switcher tile). Pages and projects never repeat a logo; a page title is plain text with no brand dot and no icon in front (decided 18 Nov), and the client name in the switcher has no dot either, because a coloured dot anywhere in CHIP means "needs attention". The red dot lives only inside the drawn logo artwork. decided 18 Nov 2026 *Check: count logos per screen (at most one per job); no dot glyph or ::after dot on titles or names.*
14. **Every doc page is an instance of the Docs Kit "Component doc page".** Its sections are Docs Kit parts (Section, Specimen, State row, Do/Don't, Properties row, Accessibility block) with content in their slots; never a hand-built frame with only the header as an instance. Moved here from Decided values (12 Nov) because the 17 Nov doc pages were built as plain frames anyway. decided 18 Nov 2026. *Check: each "· doc" board's top node is an instance of Component doc page, and the instance-override script lists no style overrides.*
15. **Cards in a row are the same height, actions on one line.** Siblings in a row stretch to the tallest (fill the cross axis), content sits at the top, the action row is pushed to the bottom, so every button lines up. decided 18 Nov 2026 Not for a list column beside a detail column: a list card hugs its rows, so no empty block hangs under three items (decided 18 Nov 2026). *Check: craft-check flags rows whose card children differ in height or don't fill.*
16. **Never clip a shadow.** A frame that holds anything with a drop shadow (cards, buttons, plates) does not clip its content, or has padding at least as big as the shadow. decided 18 Nov 2026 *Check: pixel-check CLIPPED lines and craft-check R16.*
17. **Connector lines are curved, everywhere.** Diagrams (System map, Figma paths, pipelines, flow annotations between screens) use the same rounded, curved connectors, never a mix of straight and curved. decided 18 Nov 2026 *Check: by eye on every diagram; one connector style per file.*
18. **Titles and labels come from parts, never typed text.** A flow gets the Docs Kit flow page header (breadcrumb, title, status chip, lede, "Flow N of M", links); each screen gets the Flow title banner; sections and labels use the Docs Kit part for that job. Never hand-typed text frames where a part exists. decided 18 Nov 2026. Same for component boards and section titles on flow pages (decided 18 Nov). Section titles use the coloured Docs Kit page header (colour wash, BELLA logo), the same as the flow headers, never the grey Section title (decided 18 Nov). *Check: craft-check flags loose TEXT nodes outside instances on flow and doc pages.*
19. **Cards sit on the grid, and a lone last card keeps the column above it.** The CHIP / Screen work area carries a 12-column grid (gutter spacing/24 = the card gap, margins spacing/32 = the page padding), visible on flow pages while we work. Half-width cards span 6 columns, thirds 4. Card groups use a grid (auto layout GRID) or wrap layout, never a free-fill row plus a stray card, so every card's left and right edge lines up with a card in the row above. Elleta, 18 Nov 2026, on Health "Needs you": "maybe you should turn the grid on to make sure we dont have issues like this". *Check: craft-check R19 flags a card whose edges miss the row above by more than 1px.*
20. **Beside a leading icon, the texts share one left edge.** The icon sits in its own left column; the title, the message and any lines under them stack in one text column on one left edge beside it; actions follow on the right (notifications) or below. Never put the icon in the title's row with the message running under the icon. Elleta, 18 Nov 2026, on Notification: "what happend to the notification the subtitle should be the same indent as the title". *Check: craft-check R20 (every text in a block that starts with an icon row shares one left edge, within 1px).*

## Guidelines · Token-first, always

Never hard-code a hex value, an arbitrary pixel number, or a one-off font size. If the design calls for a color, spacing, radius, or type style, it resolves through a BELLA token. If the token you need doesn't exist yet, stop and ask — do not invent one inline and move on.

Reference tokens by path (`color.brand.ochre`, `spacing.4`, `typography.font-size.base`). Consuming apps read `tokens/bella.json` as the source of truth.

**Colour is authored twice, checked once (2026-10-05).** A colour primitive is hex in `$value` and OKLCH in `$extensions.bella.oklch`; ramps hold one hue. Change both together: the build fails when they drift by ΔE2000 1 or more. Never put an OKLCH value in `$value`, and never write a hex8 tint by hand when a relative colour of its base will do. See `docs/decisions/2026-10-05-oklch-primitives.md`.

## Guidelines · The accessibility bar (recorded 2026-07-21, Elleta; re-verified 2026-09-22)

**AAA-minded AA.** Concretely:

- **Aim for AAA wherever WCAG has an AAA level** (decided 13 Nov). So: text 7:1 (labels included, not only body), targets 44×44 (2.5.5), focus ring 3px outside the control (2.4.13), hover and focus content that stays while the pointer is on it (1.4.13), status that is never colour alone. Non-text contrast has no AAA level, so controls, outlines and marks stay at 3:1 on every surface. These are settled: agents apply them without asking her.

- **AAA for ink and body text, muted included (colour B, re-verified 2026-10-04).** Light: ink 15.05 on the ground (worst), 16.13 on card; muted `cool.600` `#474c5e` 7.95 on the ground, 7.34 on inset (worst). Dark: ink 16.26 on the ground, 12.35 on raised; muted `cool.300` `#b1b7c7` 9.41 on the ground, 7.15 on raised (worst). Body text never drops below AAA on any surface.
- **Ochre is a fill, never text on light (brand refresh, 2026-09-22).** `color.brand.ochre` `#e8a83e` carries ink `cool.900` `#1d2030` text (7.76:1) in both themes. On light it is never text or a hairline (2.08:1 on white, 1.94:1 on the ground); lines and the ring on light are `color.brand.ochre-deep` `#b97a14` (3.34:1 on the ground, 3.59:1 on card). On dark, ochre clears 6.90:1 even on raised.
- **The focus ring means focus only.** 3px, 3px offset, in `color.semantic.focus-ring` (its colour per theme lives in the semantic tokens). Never at rest, never as decoration.
- **Links are ink with an underline**; hover thickens the underline to 2px (`border.width.medium`). Ink holds AAA everywhere, so link and button labels are AAA.
- **The pairs are checked, not just recorded.** `scripts/contrast-pairs.mjs` (in the gate) computes every declared foreground/background pair in both themes, plus the forbidden pairs that must stay failing.
- **Every control outline is in the contrast gate** (decided 12 Nov). The secondary Button edge was 1.58:1 and slipped through because `scripts/contrast-pairs.mjs` did not list control outlines. Every control's outline (Button secondary, Input, Select, Combobox, FilterChip, SegmentedControl, Tabs) is a 3:1 pair in the gate, against every surface it sits on. A softer look never goes below 3:1.
- **Controls clear 3:1, hairlines are decoration.** `border-strong` (`cool.500` `#686d7d` light, `cool.400` `#858b9f` dark; one step each, Elleta, 2026-10-04) is the input and control border, 3:1 on every surface: light 4.44 on inset (worst), 5.16 on card; dark 4.23 on raised (worst), 4.76 on inset, 5.13 on card. The hairline (`border` `cool.100` / `cool.800`, `border-subtle` and `border-faint` `cool.50` / `cool.850`) is decorative only and never marks a control.
- **Worst-ground-wins.** A text token passes on the *worst* surface it is allowed to sit on, or its usage metadata forbids that surface. Verified ratios are recorded per token in `$extensions.bella.a11y`, dated.

## Guidelines · Surface behavior

- Cards: `surface-card` fill, 1px `border-faint`, `radius.card` (16px), `shadow.card` at rest (Elleta, 2026-10-04; Peek stays flat), no accent-tinted border, no gradient or scrim over media. Only interactive cards (one link or one button) respond: on hover and focus-visible, `motion.transform.hover-lift` (`translateY(-2px)`) plus `shadow.hover`, over `motion.duration.lift` (200ms). No lift under reduced motion. A static card keeps its rest shadow and never changes on hover. The lift is the tell: it marks what you can click.
- Buttons: the contract wins, `tokens/component.json` → `component.button` (a flat primary plate, no gloss, no edge, never lifts; sentence case; sizes default and `sm`). Lift is reserved for cards. No trace ring on buttons; the only ring is focus. The primary contact CTA reads "Let's talk".
- One light source, upper-left: highlights top-left, shadows down-right (orbs). The elevation tokens (`shadow.orb*`, `shadow.key-*`, `shadow.switch-*`) are a token lock for the existing components: do not flatten; the depth IS the system. **The new patterns (diagrams, steps, eyebrows, callouts) carry no shadow**: 1px ink strokes and hairlines only.
- Hover transitions are quick (≤250ms) and eased. No bouncing, no spring physics.
- **Diagram motion** (style unify, 2026-09-22): `motion.duration.draw` + `motion.easing.draw` for lines, `motion.duration.pop` + `motion.easing.pop` for elements appearing, `motion.stagger.min`–`max` between steps. Plays once when in view, then holds still; reduced motion shows the finished frame. The pop overshoot is for play-once reveals only, never hover or state changes.

## Guidelines · Actions in a view (layout foundation, 2026-10-03, Elleta)

One style per job, so a page never mixes button looks for the same kind of action:

- **Main action:** at most ONE Button `primary` (sentence case: "Save changes", never "SAVE CHANGES"; Elleta, 2026-10-05) per view, and only for the action the view exists for. Zero is fine. A primary shown as a specimen (Atlas, Storybook) is content, not an action.
- **Secondary actions:** Button `secondary`.
- **Small inline actions** (on a tile, under an answer, in a list row, "Test", "Copy"): ActionChip, sentence case.
- **Navigation** (going somewhere else): Link, or NavList in a sidebar. Not a Button and not an ActionChip.
- **Filters, toggles, sort, picking a view:** FilterChip, SegmentedControl, Select. Never a Button.
- No locally styled `<button>` in a consuming app: if none of these fits, ask before inventing one.

## Guidelines · Layout rules for consumers (from RULES.md v0.2, folded 12 Nov 2026)

- **Text on a fixed dark block inside a light page** uses `--ink-on-dark-strong`, `-body`, `-muted`: they do not flip with the theme, so a dark footer keeps light ink in both modes.
- **Sibling cards share one height:** the grid `align-items: stretch`, the card `height: 100%` and a flex column, its body `flex: 1`. Never `min-height` in px on a card with variable content.
- **Card copy never truncates** (no ellipsis, no line clamp) unless the card opts in with `Card--truncate`, for listing UIs only. Shorten the copy instead.
- **Sticky headers:** set `--header-height` at `:root`, `scroll-padding-top: calc(var(--header-height) + var(--spacing-4))` on `html` and the content wrapper, and the same value as `scroll-margin-top` on anchor targets.
- **Card grids** use `repeat(auto-fill, minmax(var(--card-min), 1fr))`; a fixed `repeat(N, 1fr)` only when there are exactly N items, always. No centred widow.
- **Focus:** `outline: var(--ring-focus-width) solid var(--ring-focus-color); outline-offset: var(--ring-focus-offset)`. `outline: none` only with an equal visible replacement.
- Legacy code that breaks a rule is migrated, not grandfathered. If a rule conflicts with a comp, escalate the comp, not the rule.

## Guidelines · Aesthetic stance

Editorial. Confident. Closer to a magazine or a well-set book than a SaaS dashboard. Avoid:

- Gradient-on-gradient hero blobs
- Generic rounded-everything, pastel-everything, emoji-in-every-heading "friendly AI" UI
- Stock iconography where typography would do
- Centred text everywhere: reading text is left-aligned, and asymmetric layouts are fine. (This is about text alignment. A picture or block still sits centred in its frame or panel.)

When in doubt, the answer is more type, less chrome.

- **Check fill and hug before showing** (decided 12 Nov). Rows and cards in a stack are FILL width, so every row lines up; labels sit in a fixed-width column; the content inside a card HUGS and is centred both ways; rows in one section share one height. Before any screenshot, a script prints each row's sizing mode, x and width, and every mismatch is fixed first.
- **Look again after every fix.** A fix gets its own 100% screenshot of the section it touched before it's reported. Collapsed pills, missing text and clipped tags count as broken.
- **Say each number once** (decided 12 Nov). A bracket shows one dimension, and a tag, if there is one, adds what the bracket can't, e.g. bracket "44" plus tag "152 × 44". Never the same number twice. Tags are pills with even padding, never squashed, and never touching the text below.
- **One annotation system, everywhere** (decided 12 Nov). Taken from elleta.design's hero (`ctrl-alt-design/components/Hero.tsx`, `TokenAnnotation.tsx`): numbered pins in a fixed colour order, 1 yellow (`pop-yellow`), 2 pink (`pop-pink`), 3 blue (`pop-blue`), 4 red (`pop-red`), then repeat. Each pin is a solid filled disc in its colour with a white border and a soft shadow, numbered two-digit in Geist Mono ("01"); its leader is dashed (4/4, 1.6px) in the same colour and ends at a white full-radius pill label with a soft shadow, holding the same filled disc and the token or part name in Geist Mono ink. Size and measurement tags are filled rectangles with 2px corners in the annotation colour, never pills (decided 12 Nov). Brackets and measured-size tags belong to the annotation they explain and take its colour. Board and callout labels are the light pink wash with ink mono text. Ratios, verdicts and token names in prose stay plain ink. Use BELLA's Pin & Leader component for all of it; never draw annotations by hand.
- **The component sits to the right of its doc** (decided 12 Nov). In BellaComponents, each component's main set sits on the same page, directly to the right of its doc page frame, top-aligned, with clear space between; never on a separate page or below.
- **The rated Figma template is the doc page model** (decided 12 Nov). The look and layout of component doc pages come from the Figma template she reviewed and had rated today (324:1170, 96/100, with her later fixes: one row per state, matching pink tags, labels above shadowed specimens, specimens on Cards). Storybook follows it after all of Figma is done. Code is the source only for behaviour (what a component does), not for how the doc page looks.
- **Annotations are written from the code** (decided 12 Nov). Accessibility and Motion annotations state what the shipped component does: read each from its `.tsx`, CSS and tokens (role, name, keyboard, focus ring, disabled, aria, reduced motion, duration and easing tokens), never copied from an older Figma version. Old Figma annotations are only a checklist of topics; any that disagree with the code are corrected, and listed as changed. They go on component sets and their parts first; doc pages get theirs only after they are rebuilt from the Docs Kit components (decided 12 Nov).
- **BellaComponents holds only components and their doc pages** (decided 13 Nov). Each component page has its set and its one current doc page, nothing else. Set-aside pieces, old rounds, copies and test pages don't stay in the file: they're listed with pictures and deleted on her yes (version history keeps them). Work in progress lives on a WIP page only while it's being built.
- **A component lives only on its own page, inside its own set** (decided 13 Nov). Figma creates new components and frames on whichever page is open, not the script's page: every script appends what it creates to its target set or page in the same call, and never relies on `figma.currentPage`. Every write ends with a stray check of the pages it touched: no component whose name or content belongs to another component, no annotation that names another component, no annotations overlapping each other or covering variants. A clean-up keeps components, so a stray component is found by this check, not by the clean-up.
- **One home per thing** (decided 12 Nov). Each Figma file has a short, named page list; every component lives on one components page, grouped by job, with no two components doing the same job. Before making a piece, search the file for one that does the job and extend it. Anything replaced is set aside on one "Set aside" page, never left among live work.
- **Figma annotations come with every rebuild** (decided 12 Nov). The Figma-native annotations (Dev Mode, categories such as Accessibility and Motion) on a page or component are part of it. A rebuild lists every annotation on the old version first, carries each one over to the matching node on the new one (checked against the variables, wording kept unless a value changed), and counts old vs new before it's shown.
- **The approved page is the model.** A rebuild may not drop an approved picture or add text beyond it. An audit score that counts sections and tables is not a reason to add them.
- **One sample first.** Build one page, show it at 100%, and wait for Elleta's yes before rolling out. Never delete either the old or the new set until she says which one stays.
- **Approved frames are checked at the start and end of every write** (12 Nov, after the rated template 324:1170 vanished and no session could say when). Every agent writing in a file lists the approved frames there (ids) first and confirms they still exist when it finishes; a missing one stops the work and is reported at once, while version history still has it. Export a 100% PNG of every approved frame as soon as it's approved. Scripts remove only nodes they created in that run or nodes on a list she approved, and log every removal.
- **Work in progress never sits on a working page** (decided 12 Nov). Half-built pieces are made on their own page ("WIP · <date> · <what>") and move to the working page only when finished, in clear space. Every write ends with an overlap and loose-node check of the page it touched.

Bad: a Type page that opens with a ten-line "type lock" box, then a table of sizes. Good: every size set at its real size with a bracket and token name, and a pink line marking the 16px floor. Why: she reads the system from pictures; the table makes her read.

## Governance · Building a new component (decided 12 Nov 2026)

Order: Switch, Input password with show/hide, Dialog, destructive Button, Pagination (Select's error state shipped 25 Nov 2026). One at a time; the next starts only after her yes on the last.

**Machine-readable before code.** The 12 Nov rule "all of Figma first" is replaced by "Code starts page by page" (18 Nov, near the top): each page goes to code on its own once it meets that bar. Existing components meet this bar too (see "Fix the component before its doc page" below). Before code, a fresh agent checks that Figma is machine-readable:
- every colour, size, radius, gap and type value bound to a BELLA variable, none raw;
- variant and property names and values identical to the React props (`variant`, `size`, `checked`, `disabled`…);
- layers named by part (Track, Thumb, Label), auto layout throughout, no detached instances or drawn stand-ins;
- each component's description follows the one pattern the other components already use (decided 12 Nov). Copy that shape part for part; never replace a description with a single build note (those go in annotations). Set the Storybook link set as its documentation link;
- annotations are Pin & Leader instances, specimens sit on Card instances.
Fails get fixed before any code.
- **Look first.** Check BellaComponents, the Docs Kit and her private layout exports (layout only, no names or tokens from them) for one that exists. Extend before making new.
- **Figma first.** Build the component set in BellaComponents from BELLA variables only: no raw colours, sizes or radii. Variant properties use the same names and values the React props will use.
- **The bar is built in.** 44px target, the theme's focus ring (pink in Chip), body and label contrast per "The accessibility bar", every outline at least 3:1 on page, panel and stone stage. Every state drawn: default, hover, pressed, focus, disabled, and error or checked where it applies.
- **One sample, then her yes.** Show the set at 100% beside one doc page built from the Docs Kit template, after a fresh agent has rated it 5/5 and checked it for overlaps and loose nodes. Code waits for "All of Figma first" above.
- **Code matches Figma.** React component, CSS Modules on tokens, stories for every variant, contrast pairs added to the gate, `npm run gate` green. Then the Figma-vs-code check: each variant on white and on black, size within 2px, every label and icon present, right colours. Anything it can't measure counts as a fail.
- **Fix the component before its doc page** (decided 12 Nov). Per component: run `scripts/spec-build.mjs` (code + Figma); its `mismatch` list is the work list. Fix the set in BellaComponents to the machine-readable bar above; code wins on behaviour and values unless she approved the Figma look, and every disagreement is listed. Re-spec until `mismatch` is empty or explained. Only then generate the doc page and run `figma-doc-check.js`. CHIP's designs are rebuilt from the fixed components after that.
- **Clean, not set aside** (decided 15 Nov 2026). Delete what is replaced or unused in the same step and list it in the report; her approved frames and published components only after she sees the list. Nothing is committed, published or merged without her OK.

## Guidelines · Tiered inheritance

Repos that install BELLA as a `devDependency` inherit this AGENTS.md automatically. They may add their own `AGENTS.md` at their root to layer additional rules — but downstream rules only *extend* or *tighten* BELLA's. They do not relax them. A consuming repo cannot, for example, use pure white off the page ground, drop body text to 14px, put colour in a stroke outside focus and status, set ochre as text on light, or set any text below 16px.

If a consuming repo's rules conflict with BELLA's, BELLA wins. Flag the conflict; don't silently resolve it.

## Guidelines · Data marks (2026-10-03, Elleta)

Data marks (sparklines, charts) may use inline SVG, marked `data-bella-diagram`, and must carry an accessible text equivalent: `role="img"` with an `aria-label` that says what the mark shows (Stat's sparkline: "Stories: 18 to 22 over 22 syncs"). Same drawing rules as diagrams: ink strokes, chip fills, no state colour.
